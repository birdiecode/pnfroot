# pnfroot

pnfroot — это экспериментальный rootless контейнерный runtime для Linux, ориентированный на реализацию Kubernetes Container Runtime Interface (CRI). Проект задумана как альтернатива традиционным privileged runtime, которым для создания контейнеров, пространств имён и сетевых ресурсов требуется запуск от имени root. Вместо этого pnfroot стремится работать в пользовательском пространстве и предоставлять стандартный gRPC-интерфейс CRI, который может использовать Kubernetes через kubelet.

## Что это такое

pnfroot предназначен для экспериментов с контейнерным выполнением без привилегий. Идея проекта — показать, что контейнерный рантайм может быть реализован как пользовательский процесс, который взаимодействует с Kubernetes через стандартный CRI-интерфейс, не полагаясь на запуск под root.

Такой подход полезен для:

- исследований в области rootless контейнеризации;
- экспериментальных окружений и учебных проектов;
- разработки альтернативных моделей изоляции и исполнения;
- интеграции с Kubernetes в сценариях, где запуск privileged-демонов невозможен или нежелателен.

## Ключевые особенности

- CRI-compatible runtime: поддержка взаимодействия с Kubernetes через стандартный интерфейс Container Runtime Interface.
- Rootless execution: запуск без необходимости использования привилегий root.
- Экспериментальный характер: проект не предназначен для production-использования и продолжает развиваться.
- ptrace-based execution model: поведение контейнерных процессов контролируется на уровне системных вызовов.
- Виртуальная сеть: в составе проекта есть механизмы для создания изолированных сетевых сценариев и внешних точек входа.

## Почему это важно

Kubernetes ожидает, что контейнерный runtime реализует CRI. Это даёт возможность подключать pnfroot как обычный runtime для kubelet, не меняя сам механизм взаимодействия с Kubernetes. В результате runtime может быть использован в экспериментальных кластерах, CI-средах или исследовательских установках, где важны простота, переносимость и отсутствие требования к root.

## Текущий статус проекта

pnfroot находится на ранней стадии разработки. Основной акцент сейчас делается на демонстрации идеи rootless-исполнения и взаимодействия с Kubernetes через CRI. В текущем состоянии проект уже включает элементы ptrace-ориентированного исполнения и виртуальной сети, но его функциональность ещё ограничена и не рассчитана на полноценное production-использование.

Важно отметить, что CRI в проекте реализован лишь частично: сейчас основное внимание сосредоточено на самой контейнеризации и базовом исполнении процессов, а не на полном, production-grade покрытии всего CRI-спецификатора. То есть проект пока лучше рассматривать как экспериментальный runtime-провайдер для изучения и прототипирования, а не как готовую замену Docker, containerd или CRI-O.

## Архитектура

Проект строится вокруг нескольких взаимосвязанных компонентов:

1. CRI-слой
   - принимает gRPC-запросы от kubelet;
   - обеспечивает обработку запросов на создание, запуск, остановку и удаление контейнеров.

2. Исполнитель контейнеров
   - запускает процессы в пользовательском режиме;
   - использует ptrace для наблюдения и контроля системных вызовов.

3. Слой файловой системы и окружения
   - формирует контейнерное окружение;
   - поддерживает rootfs, bind mounts и другие пользовательские примитивы.

4. Слой сети
   - предоставляет виртуальные интерфейсы и изолированные сетевые сценарии;
   - позволяет организовывать взаимодействие между контейнерами и внешним миром без создания обычных host-namespace.

## Как он работает

На практике runtime перехватывает системные вызовы процессов, выполняемых внутри контейнера, и эмулирует необходимые для них операции в пользовательском пространстве. Это позволяет избегать прямого использования привилегированных возможностей ядра, характерных для стандартных контейнерных runtime, и при этом сохранять достаточную основу для запуска и управления контейнерными рабочими нагрузками.

## Примеры запуска

Базовый запуск процесса под трасировкой:

```bash
./ptrace_syscalls.py -- /bin/ls -la
./ptrace_syscalls.py --rootfs ./ubuntu_c -- /bin/bash
./ptrace_syscalls.py --rootfs ./ubuntu_c --uid 0 --gid 0 -- /bin/bash
./ptrace_syscalls.py --rootfs ./ubuntu_c --bind /tmp:/host-tmp -- /bin/ls /host-tmp
```

Для использования с виртуальной сетью сначала запускают сетевой сервис:

```bash
python3 -m netservice.server \
  --socket /tmp/net.unix \
  --internet-networks testnet \
  --log
```

После этого можно запустить контейнер с виртуальным интерфейсом:

```bash
./ptrace_syscalls.py \
  --netdev name=eth0,network=backend \
  --netservice /tmp/net.unix \
  -- /bin/bash
```

## Принципы дизайна

- Минимализм и прозрачность.
- Отказ от зависимости от root в обычном сценарии запуска.
- Поддержка стандартных интерфейсов, таких как CRI.
- Возможность постепенного расширения функциональности.
- Акцент на экспериментальной проверке идей, а не на готовом production-решении.

## Ограничения

Поскольку проект находится в начальной стадии, у него есть ряд ограничений:

- функциональность пока не соответствует полноценным production runtime;
- часть поведения может быть ограничена по сравнению с Docker, containerd или CRI-O;
- поддержка сложных сценариев контейнеризации требует дальнейшей разработки;
- rootless-подход вносит дополнительные ограничения на доступ к системным ресурсам.

## Планы развития

В дальнейшем планируется расширять pnfroot в следующих направлениях:

- полная или более широкая реализация CRI-операций;
- улучшение управления жизненным циклом контейнеров;
- расширение поддержки файловой системы и bind mounts;
- развитие сетевого стека и виртуальных интерфейсов;
- повышение совместимости с Kubernetes и стандартными сценариями запуска.

## Заключение

pnfroot — это попытка создать экспериментальный, rootless контейнерный runtime, который можно использовать с Kubernetes через CRI. Проект показывает, что контейнерный стек может быть реализован в более доступной и менее привилегированной модели, сохраняя при этом совместимость с широко используемым стандартом Kubernetes.

Это исследовательский проект, который полезен как для изучения архитектуры контейнерных runtime, так и для прототипирования новых подходов к изоляции и управлению workload в Kubernetes.
